Zig: The First 30 Minutes

Only the Zig you need to build Monk. Not a full tutorial — a survival guide. You'll learn more as each phase demands it.

zig 30 min read

Why Zig?

Zig is C with better ergonomics. No hidden allocations, no hidden control flow, no garbage collector. You always know what the computer is doing.

If you know any C-family language (C, Go, JS, Java), Zig will look familiar. The differences are what make it better for building a compiler.

Variables

// Immutable — cannot change after assignment const x: i64 = 42; const name = "hello"; // type inferred // Mutable — can change var counter: i64 = 0; counter = 10; counter += 1;

const is the default mindset. Use var only when you need mutation. Same philosophy as Monk.

Types you'll use

i6464-bit signed integer (Monk's int)
f6464-bit float (Monk's float)
boolBoolean

[]const u8Immutable string (what you'll use most)

Functions

// Basic function fn add(a: i64, b: i64) i64 { return a + b; } // Function that can fail fn divide(a: i64, b: i64) !i64 { if (b == 0) return error.DivisionByZero; return @divTrunc(a, b); }

The ! before the return type means "this function can return an error." Zig forces you to handle errors — you can't ignore them.

// Calling a function that might fail const result = divide(10, 3) catch |err| { std.debug.print("Error: {}\n", .{err}); return; };

Compare with Monk: Zig's catch is like Monk's guard...against. Both make error handling explicit. No hidden exceptions.

Structs

Structs are how we build everything in the compiler — tokens, AST nodes, values. They're like records in Monk or objects in JS, but typed and fixed.

const Token = struct { kind: TokenKind, lexeme: []const u8, line: u32, column: u32, }; // Create a struct value const tok = Token{ .kind = .identifier, .lexeme = "hello", .line = 1, .column = 5, }; // Access fields with dot notation std.debug.print("{s}\n", .{tok.lexeme});

Fields are initialized with .field_name = value. Every field must be set — no defaults, no partial initialization.

Enums

Enums define a fixed set of choices. We use them for token types, operator kinds, and AST node categories.

const TokenKind = enum { // Literals number, string, identifier, // Keywords kw_let, kw_const, kw_if, // Operators plus, minus, equals, // Special eof, }; const kind = TokenKind.plus; // Switch on an enum — must handle ALL cases switch (kind) { .plus => std.debug.print("+", .{}), .minus => std.debug.print("-", .{}), else => {}, }

Exhaustive switches. Zig's switch must handle every enum variant. If you add a new token type, the compiler tells you everywhere you forgot to handle it. This catches bugs early.

Tagged Unions

The most important Zig feature for us. A tagged union is a value that can be one of several types. This is how we represent AST nodes — an expression can be a number, a string, a binary operation, a function call, etc.

const Expr = union(enum) { number: f64, string: []const u8, boolean: bool, none: void, binary: BinaryExpr, identifier: []const u8, }; const BinaryExpr = struct { left: *Expr, // pointer to another expression op: TokenKind, right: *Expr, };

You pattern-match on the active variant with switch:

fn describe(expr: Expr) void { switch (expr) { .number => |n| std.debug.print("number: {d}\n", .{n}), .string => |s| std.debug.print("string: {s}\n", .{s}), .boolean => |b| std.debug.print("bool: {}\n", .{b}), .binary => |bin| { std.debug.print("binary op\n", .{}); }, else => {}, } }

Analogy

A tagged union is like a shipping box with a label on it. The label says "books" or "electronics" or "fragile." You don't open the box to know what kind of thing is inside — you read the label. In code, the "label" is the enum tag, and the "contents" is the associated data.

Optionals

An optional is either a value or null. Zig forces you to check before using it. No null pointer crashes.

// The ? means "might be null" fn find(haystack: []const u8, needle: u8) ?usize { for (haystack, 0..) |char, i| { if (char == needle) return i; } return null; } // Must unwrap before using if (find("hello", 'l')) |index| { std.debug.print("found at {d}\n", .{index}); } else { std.debug.print("not found\n", .{}); }

Compare with Monk: Zig's ?T is like Monk's int?. Same concept — a value that might not be there. Both languages make you deal with it explicitly.

Slices and Arrays

// Fixed-size array (lives on the stack) const arr = [_]i64{ 1, 2, 3, 4, 5 }; // Slice — a pointer + length (like a view into an array) const slice: []const i64 = arr[1..3]; // [2, 3] // Strings are just byte slices const greeting: []const u8 = "Hello"; const len = greeting.len; // 5

A slice points into the original array. No copy made.

Slices are everywhere in Zig. The lexer reads a []const u8 (the source code). Tokens store []const u8 slices pointing back into the source. No copying.

Allocators and defer

In most languages, memory appears out of thin air. In Zig, you choose where it comes from. This matters when we build the AST — tree nodes live on the heap.

// Create an allocator (catches leaks in debug mode) var gpa = std.heap.GeneralPurposeAllocator(.{}){}; defer _ = gpa.deinit(); // reports leaks when program exits const allocator = gpa.allocator(); // Allocate a single value on the heap const ptr = try allocator.create(Expr); defer allocator.destroy(ptr); // freed when scope exits // Allocate an array on the heap const buf = try allocator.alloc(u8, 1024); defer allocator.free(buf);

defer is Zig's cleanup mechanism. It runs the statement when the current scope exits — no matter how (return, error, break). Think of it as "undo this when I leave."

// Dynamic array (growable list) var list = std.ArrayList(i64).init(allocator); defer list.deinit(); try list.append(42); try list.append(99); std.debug.print("length: {d}\n", .{list.items.len}); // 2

We use ArrayList for collecting tokens in the lexer and statements in the parser. Grows as needed, freed with defer.

Testing

Zig has built-in testing. No framework to install. This is what we use for TDD — write the test first, watch it fail, make it pass.

const std = @import("std"); fn add(a: i64, b: i64) i64 { return a + b; } test "addition works" { try std.testing.expectEqual(@as(i64, 5), add(2, 3)); } test "negative numbers" { try std.testing.expectEqual(@as(i64, -1), add(2, -3)); }

Run tests

$ zig build test All 2 tests passed.

Printing

// Debug printing (for development) std.debug.print("value: {d}\n", .{42}); std.debug.print("name: {s}\n", .{"hello"}); std.debug.print("bool: {}\n", .{true}); // Format specifiers: // {d} — integer // {s} — string (byte slice) // {} — default format // {any} — any type

String comparison

Zig strings are byte slices. You can't compare them with == (that compares pointers). Use std.mem.eql:

const a = "hello"; const b = "hello"; // Wrong — compares pointers, not contents // if (a == b) { ... } // Right — compares byte contents if (std.mem.eql(u8, a, b)) { std.debug.print("equal\n", .{}); }

This comes up constantly in the lexer when checking if an identifier matches a keyword like "let" or "const".

What you don't need yet

Comptime (compile-time execution) — powerful, not needed until Phase 3+
Async — not needed at all
SIMD — not needed
Build system details — zig build test is enough to start

Each phase introduces new Zig concepts as needed. You'll never learn something you don't immediately use.

Key takeaways

1

const and var — immutable by default, explicit mutation.

2

Structs for data, enums for choices, tagged unions for "one of many" — these build the compiler's core data structures.

3

Allocators give you explicit memory. defer cleans up. No hidden garbage collection.

4

Testing is built in. zig build test runs everything. No setup needed.
